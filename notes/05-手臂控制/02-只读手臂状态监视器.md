## 1. 这是什么

`arm_state_monitor` 只订阅 H1-2 的 `rt/lowstate`，显示左右臂和腰部共 15 个关节的状态，并检查消息频率与新鲜度。

它不创建 Publisher，也不调用 `Write()`，因此程序自身没有发送手臂运动命令的路径。

## 2. 为什么抓取任务需要它

抓取控制器不能只发送目标，还必须持续判断：

- 是否真正收到机器人状态。
- 状态是否已经过期。
- 实际关节是否跟随目标。
- 关节速度和估计力矩是否异常。

这个监视器先建立可靠的状态输入，未来可复用于轨迹控制器、安全监督器和抓取状态机。

## 3. 数据流

```text
机器人
  │ rt/lowstate（LowState_）
  ▼
DDS 回调线程
  │ 加锁并更新 StateCache
  ▼
线程安全状态缓存
  │ 主线程加锁复制快照
  ▼
局部 snapshot
  │ 解锁后计算和打印
  ▼
q / dq / tau_est / 接收频率 / 状态年龄
```

## 4. 只读边界

程序只包含：

```cpp
unitree::robot::ChannelSubscriber<LowState> subscriber(kTopicState);
```

不包含：

```cpp
ChannelPublisher<LowCmd_>
Write(msg)
```

运行前仍需检查实际执行的是本程序，而不是官方运动例程。只读软件也不能代替现场电气和人员安全规范。

## 5. 关节范围

| 数量 | SDK index | 关节 |
|---:|---|---|
| 7 | `13~19` | 左臂 |
| 7 | `20~26` | 右臂 |
| 1 | `12` | WaistYaw |

程序使用 `JointInfo` 同时保存 SDK index 和可读名称，避免打印时只看到数字编号。

## 6. `StateCache`

```cpp
struct StateCache {
  std::mutex mutex;
  LowState latest_state;
  Clock::time_point last_receive_time{};
  std::uint64_t message_count{0};
  bool received{false};
};
```

| 字段 | 作用 |
|---|---|
| `mutex` | 防止回调写入时主线程同时读取 |
| `latest_state` | 保存最新完整状态 |
| `last_receive_time` | 记录最后一帧到达的本机单调时间 |
| `message_count` | 统计收到的消息总数 |
| `received` | 区分“从未收到”与“曾经收到” |

## 7. 回调写入与主线程快照

DDS 回调收到状态后：

```text
检查消息指针
→ 转换为 LowState 指针
→ 加锁
→ 复制状态
→ 更新时间和数量
→ received=true
→ 自动解锁
```

主线程不会长时间直接使用共享对象，而是：

```text
加锁
→ 把共享状态复制到局部 snapshot
→ 解锁
→ 使用 snapshot 计算并打印
```

打印终端可能较慢，所以必须在解锁后进行，避免阻塞 DDS 回调接收下一帧。

## 8. 状态有效性

只使用 `received` 不够：断网后它仍会保持 `true`。程序还会计算：

```text
state_age = 当前时间 - last_receive_time
```

状态分为：

```text
received=false                 → 从未收到状态
received=true 且 age≤500ms     → FRESH
received=true 且 age>500ms     → STALE
```

`500 ms` 当前只是监视器的初始显示阈值，不是已经验证的运动安全阈值。实机记录真实频率后需要重新确定。

## 9. 接收频率

```text
receive_rate = 本报告周期新增消息数 / 实际经过秒数
```

例如 1.5 秒内计数从 1000 增加到 1450：

```text
(1450 - 1000) / 1.5 = 300 Hz
```

使用实际经过时间，是因为 `sleep_for(1s)` 加上计算和调度后并不保证报告间隔严格等于 1 秒。

## 10. Ctrl+C 退出

信号处理函数只设置：

```cpp
g_stop_requested = 1;
```

不在信号处理函数中打印、获取 mutex 或调用 DDS。信号可能在主线程持锁或库函数运行期间到来，执行复杂操作可能造成死锁或状态损坏。

主线程看到停止标志后退出循环、关闭 Subscriber，再正常结束程序。

当前报告周期为 1 秒，所以退出可能稍有延迟。只读监视器没有发送动作，这个延迟只影响程序退出速度；未来运动控制器不能直接照搬。

## 11. DDS 异常处理

DDS 初始化和运行部分放在 `try` 内。网卡无效、DDS domain 创建失败等异常会被 `catch` 捕获：

```text
打印明确错误
→ 返回退出码 2
→ 不产生 core dumped
```

本次受限环境中的回环测试无法创建 DDS domain。修改前程序异常中止，退出码为 134；加入异常处理后能够受控退出，退出码为 2。

## 14. 已掌握的关键点

- Subscriber 只接收，不需要创建 Publisher。
- `received=true` 只能证明曾经收到，不能证明状态仍然新鲜。
- 回调写共享状态、主线程读共享状态时需要同步。
- 主线程应复制快照后尽快释放 mutex，再进行耗时打印。
- 信号处理函数只设置简单标志，清理工作由正常流程完成。
- DDS 初始化失败应明确报错并受控退出。
