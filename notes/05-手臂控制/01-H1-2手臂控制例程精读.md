> 本笔记以本机实际 SDK 源码为准。官方源码保持只读；后续安全增强程序放在本学习仓库的 `code/` 下。

## 1. 这是什么（一句话概括）

这个例程订阅 H1-2 的全身低层状态，再通过专用的 `rt/arm_sdk` 话题控制左右两条 7 自由度手臂和腰部偏航关节。

虽然消息类型叫 `LowCmd_`，它发布到的是 `rt/arm_sdk`，不是全身低层控制话题 `rt/lowcmd`。因此它属于手臂 SDK 接口，不能仅凭消息类型把它当成全身低层控制。

## 2. 为什么抓取任务需要它

视觉抓取最终要把规划得到的手臂关节目标持续发送给机器人，同时读取真实关节反馈。这个例程展示了最小数据链路：

```text
机器人关节状态
    │  rt/lowstate（LowState_）
    ▼
用户程序：读取 q，生成 q_des，填写 kp/kd/dq/tau
    │  rt/arm_sdk（LowCmd_）
    ▼
机器人内部手臂控制服务
    ▼
左右臂 + WaistYaw
```

它可以作为理解接口的起点，但缺少我们实机抓取所需的完整安全检查，不能原样作为第一次实机测试程序。

## 3. 两个 DDS 话题

| 方向 | Topic | 消息类型 | 在例程中的用途 |
|---|---|---|---|
| 机器人 → 程序 | `rt/lowstate` | `unitree_hg::msg::dds_::LowState_` | 读取关节实际位置等反馈 |
| 程序 → 机器人 | `rt/arm_sdk` | `unitree_hg::msg::dds_::LowCmd_` | 发送手臂目标与控制参数 |

通信通过下面这行初始化：

```cpp
unitree::robot::ChannelFactory::Instance()->Init(0, argv[1]);
```

- `0` 是 DDS domain id。
- `argv[1]` 是运行程序时传入的网卡名。
- 参数不足时程序会输出 `Usage: 程序名 networkInterface` 并退出。

## 4. H1-2 关节编号

这个版本的 `LowCmd_` 和 `LowState_` 都包含 35 个电机槽位。H1-2 实际关节使用索引 `0~26`；例程用索引 `27` 的 `q` 字段传递手臂 SDK 权重，`28~34` 在枚举中标为未使用。

### 4.1 全身编号

| 范围 | 含义 |
|---|---|
| `0~5` | 左腿 |
| `6~11` | 右腿 |
| `12` | `WaistYaw` |
| `13~19` | 左臂 7 关节 |
| `20~26` | 右臂 7 关节 |
| `27` | 本例程用作 arm SDK weight，不是实体关节 |
| `28~34` | 未使用槽位 |

### 4.2 手臂关节表

| 控制数组序号 | SDK index | 左臂 | 控制数组序号 | SDK index | 右臂 |
|---:|---:|---|---:|---:|---|
| 0 | 13 | LeftShoulderPitch | 7 | 20 | RightShoulderPitch |
| 1 | 14 | LeftShoulderRoll | 8 | 21 | RightShoulderRoll |
| 2 | 15 | LeftShoulderYaw | 9 | 22 | RightShoulderYaw |
| 3 | 16 | LeftElbow | 10 | 23 | RightElbow |
| 4 | 17 | LeftWristRoll | 11 | 24 | RightWristRoll |
| 5 | 18 | LeftWristPitch | 12 | 25 | RightWristPitch |
| 6 | 19 | LeftWristYaw | 13 | 26 | RightWristYaw |
| 14 | 12 | WaistYaw | - | - | - |

`arm_joints` 的顺序是“左臂 7 个 → 右臂 7 个 → 腰部 1 个”，因此后面的 15 维 `kp_array`、`kd_array`、`init_pos` 和 `target_pos` 必须严格使用同一顺序。

> 这只是 SDK index 表。关节正方向、机械零位、位置/速度/力矩限位仍需与 H1-2 URDF和厂家资料交叉验证。

## 5. 单个电机命令和状态包含什么

### 5.1 `MotorCmd_`

| 字段 | 含义 |
|---|---|
| `mode` | 电机/控制模式；本例程没有主动填写 |
| `q` | 目标关节位置；例程的主要控制量 |
| `dq` | 目标关节速度；例程统一设为 0 |
| `tau` | 前馈力矩；例程统一设为 0 |
| `kp` | 位置误差比例增益 |
| `kd` | 速度误差阻尼增益 |
| `reserve` | 保留字段 |

概念上的控制关系是：

```text
tau_command = kp * (q_des - q_measured)
            + kd * (dq_des - dq_measured)
            + tau_ff
```

### 5.2 `MotorState_`

包含 `q`、`dq`、`ddq`、`tau_est`、温度、电压和状态字段。当前官方例程实际只读取了 `q`，后续安全监视器还需要使用时间戳/到达时间、`dq`、`tau_est` 和状态字段。

### 5.3 PD 闭环实际在哪里

这个用户程序没有直接计算 `kp(q_des-q_measured)+kd(dq_des-dq_measured)+tau_ff`，而是把 `q/dq/kp/kd/tau_ff` 写入消息，交给机器人内部控制器结合真实反馈执行关节闭环。

需要区分两层闭环：

```text
机器人内部关节闭环：根据关节误差驱动电机趋近目标
用户程序监督闭环：检查状态超时、跟踪误差、限位和任务是否完成
```

官方示例只在运动前读取一次实际角度。运动期间虽然 Subscriber 仍可能更新 `state_msg`，但控制循环只更新自己生成的 `current_jpos_des`，没有重新读取反馈并计算跟踪误差。因此它缺少抓取系统需要的用户层监督闭环。

## 6. 官方例程的执行过程

### 阶段 1：建立 DDS 通信

1. 使用指定网卡初始化 DDS。
2. 创建 `rt/arm_sdk` Publisher。
3. 创建 `rt/lowstate` Subscriber。
4. 回调函数收到状态后，用 `memcpy` 把消息复制到 `state_msg`。

订阅队列长度传入 `1`，目标是只保留很少的待处理状态，避免控制程序处理过旧数据。

### 阶段 2：读取当前关节角并进入初始姿态

按回车后，例程读取 15 个受控关节的当前 `q`。随后用 2 秒线性插值，从当前姿态过渡到：

- 左肩 Roll：`+0.3 rad`（约 `+17.2°`）
- 右肩 Roll：`-0.3 rad`（约 `-17.2°`）
- 其他受控关节：`0 rad`

但循环中会立即执行：

```cpp
weight = 1.0;
msg.motor_cmd().at(JointIndex::kNotUsedJoint).q(weight);
```

也就是直接把 arm SDK 权重设为 1，没有渐进接管。

### 阶段 3：抬臂并放下

第二次按回车后：

1. 左右肩 Roll 分别向 `+90°/-90°` 运动。
2. 左右肘都向 `+90°` 运动。
3. 其余腕部和腰部目标为 0。
4. 随后按相同方法返回初始姿态。

每个周期的目标变化使用 `std::clamp` 限制在 `±max_joint_delta`。

### 阶段 4：降低控制权重

程序最后尝试减小 weight，然后退出。

## 7. 控制周期和速度限制计算

```cpp
control_dt = 0.02 s
max_joint_velocity = 0.5 rad/s
max_joint_delta = max_joint_velocity * control_dt
                = 0.01 rad/周期
```

因此名义控制频率为：

```text
1 / 0.02 = 50 Hz
```

每周期最多改变 `0.01 rad`，约为 `0.573°`。这是对“发送目标位置变化率”的限制，不等于已经验证了真实关节速度，也不限制加速度和冲击。

## 8. 源码安全审查：为什么现在不能直接运行

### 8.1 没有等待第一帧有效状态

`state_msg` 默认构造为全零。程序虽然等待用户按回车，但没有变量确认回调至少成功执行过一次。如果 DDS 没连通，所谓“当前姿态”可能全部被读成 0。

### 8.2 状态读取存在并发数据竞争风险

DDS 回调线程用 `memcpy` 写 `state_msg`，主线程同时读取它，没有互斥锁或双缓冲。可能读到一次更新过程中的不一致数据。

### 8.3 控制权重直接跳到 1

定义了 `weight_rate`，但接管阶段没有使用它，而是立即设置 `weight = 1.0`。第一次接管时应先确认 weight 的真实语义和机器人端行为，再设计无突变接管。

### 8.4 “停止”阶段没有把 weight 降到 0

源码参数为：

```text
weight_rate = 0.2 /s
stop_time = 2.0 s
```

2 秒最多只会让 weight 从 `1.0` 降低约 `0.4`，结束时仍约为 `0.6`。程序退出后机器人端如何处理发布者消失，需要从官方资料或实机只读行为进一步确认，不能假设已经安全释放。

### 8.5 缺少抓取系统需要的保护

- 没有检查 `rt/lowstate` 是否超时。
- 没有检查 `Write()` 是否成功。
- 没有关节位置、速度和加速度限位。
- 没有跟踪误差阈值。
- 没有监控 `dq`、`tau_est`、电机状态和温度。
- 没有处理 `Ctrl+C` 或其他异常退出。
- 没有检查目标姿态是否自碰撞或碰撞环境。
- 没有确认当前机器人 FSM 是否接受 `rt/arm_sdk`。
- 没有确认是否有其他程序同时占用手臂控制话题。

### 8.6 示例目标不是我们的抓取准备姿态

官方示例的 `init_pos` 和 `target_pos` 用来展示双臂运动，不能因为它们写在官方代码里就认定适合当前机器人现场、吊绳状态或未来 Dex5 抓取。

## 9. 当前结论

### 已确认

- H1-2 每条手臂有 7 个关节。
- 该例程同时控制左右臂和 `WaistYaw`，共 15 个关节。
- 状态来自 `rt/lowstate`，手臂指令发往 `rt/arm_sdk`。
- 关节目标使用 `LowCmd_.motor_cmd[index]` 的 `q/dq/kp/kd/tau` 字段。
- SDK weight 借用索引 27 的 `q` 字段传递。
- 名义控制周期为 20 ms，即 50 Hz。

### 尚未确认

- weight 在 H1-2 机器人端的精确定义、混合公式和掉线处理。
- `rt/arm_sdk` 可用的机器人 FSM、控制权互斥规则。
- 各手臂关节的准确限位、正方向和安全增益范围。
- 程序退出或网络中断后的机器人端超时行为。
- 安装 Dex5 后是否需要更新负载、模型或控制参数。

## 10. 与最终抓取对应的下一步

第一份自定义程序不发送任何命令，只实现：

```text
arm_state_monitor
├── 等待第一帧状态
├── 打印 15 个手臂/腰部关节的位置和速度
├── 统计消息接收频率
├── 检测状态超时
└── 将数据记录为可离线分析的日志
```

它直接服务于未来抓取任务中的状态反馈、故障检测和日志系统，并且不会引起机器人运动。

## 11. 我的理解检查

- [x] `InitChannel()` 是否已经发送消息？
  - 没有，它只建立通信通道；真正发送消息的是 `arm_sdk_publisher->Write(msg)`。
- [x] 创建 Subscriber 后是否可以直接认为已经收到机器人状态？
  - 不可以。必须由回调执行并设置“已收到第一帧”的标志或更新时间，主线程才能确认状态有效。
- [x] 为什么不能让 DDS 回调线程和主线程直接共用 `state_msg`？
  - DDS 回调线程会写入 `state_msg`，主线程会读取它。两者并发访问且没有同步时，主线程可能读到一次更新过程中的不一致状态。
- [x] 为什么使用 `LowCmd_` 消息不等于使用 `rt/lowcmd` 全身低层控制？
  - `LowCmd_` 只是消息的数据格式；该例程的接收地址是 `rt/arm_sdk`，不是全身低层控制话题 `rt/lowcmd`。
- [x] 为什么 `arm_joints` 数组的顺序不能随意修改？
  - `target_pos`、增益等 15 维数组按照同一顺序与关节对应。只改变 `arm_joints` 会把目标角发给错误关节，产生意外运动。
- [x] `control_dt = 0.02` 对应多少 Hz？
  - 名义频率为 `1/0.02 = 50 Hz`。5 秒运动对应 `5/0.02 = 250` 次循环。
- [x] 为什么 `sleep_for(20ms)` 不能保证严格的 50 Hz？
  - 每次循环还包含更新目标、填写 15 个关节命令、DDS 发送和系统调度时间，所以实际周期是这些耗时再加 20 ms，实际频率可能低于 50 Hz。
- [x] 控制数组序号 `j` 和 SDK index 是否相同？
  - 不同。`j` 是 15 维紧凑控制数组的序号；`arm_joints[j]` 才是 35 槽消息中的 SDK index。例如 `j=3` 最终写入左肘对应的 `motor_cmd[16]`。
- [x] 只改变 `arm_joints` 顺序而不调整其他 15 维数组有什么风险？
  - 目标角、初始角和增益会被映射到错误关节。即使某些增益数值碰巧相同，整体对应关系仍然错误。
- [x] `max_joint_delta` 限制的究竟是目标变化率还是真实速度？
  - 它只限制相邻两次目标角命令的变化量。真实关节速度还受 PD 增益、负载、摩擦、电机能力和内部控制器等因素影响。
- [x] 当剩余误差小于 `max_joint_delta` 时，`std::clamp` 会怎样处理？
  - 直接使用剩余误差。例如 `clamp(0.005, -0.01, 0.01) = 0.005`，因此可以到达目标而不会越过。
- [x] 关节角线性变化能否保证手腕沿直线运动？
  - 不能。关节角经过包含三角函数的非线性正运动学映射后，手腕一般形成曲线；直线接近物体需要在笛卡尔空间规划路径，再通过逆运动学求关节角。
- [x] 如果尚未收到 `rt/lowstate`，当前官方例程可能读取到什么？
  - 可能把默认的全零状态当成真实关节角。若真实姿态不是零位，随后把 weight 设为 1 可能产生很大的控制作用。
- [x] `max_joint_velocity` 是否限制了进入 `init_pos` 的初始化运动？
  - 没有限制。初始化循环只按 2 秒固定时间使用 phase 插值，没有使用 `max_joint_delta` 或 `std::clamp`；其平均目标变化速度约为 `|init_pos-current_jpos|/2s`。
- [x] `dq_des = 0` 是否意味着关节不会运动？
  - 不意味着。只要 `q_des-q_measured` 不为零，位置控制项仍会推动关节趋近目标。
- [x] 当目标角等于实际角但关节仍在运动时，哪一项仍可能产生作用？
  - `kd(dq_des-dq_measured)` 阻尼项。例程中 `dq_des=0`，因此它会对实际关节速度产生反向作用。
- [x] 同样的位置误差下，`kp` 从 50 增加到 100 会怎样？
  - 位置控制项 `kp(q_des-q_measured)` 增大为原来的两倍。
- [x] 为什么当前的 stop 循环不能把 weight 从 1 完全降到 0？
  - 每周期减少 `0.2 × 0.02 = 0.004`，2 秒约执行 100 次，总共只减少约 `0.4`，最终仍约为 `0.6`。
- [x] `weight = 0` 是否等于手臂零力矩？
  - 不等于。当前只能确认 weight 表示 arm SDK 的控制权重；机器人端混合和退出行为尚无明确依据，不能把释放 arm SDK 控制权解释为电机零力矩。
- [x] 用户程序是否直接计算了 PD 控制力矩？
  - 没有。程序只发送 `q/dq/kp/kd/tau_ff`，机器人内部控制器再结合真实反馈执行关节闭环。
- [x] `current_jpos_des` 是真实反馈还是期望角？
  - 是程序自己生成的当前期望角，不是机器人实际关节反馈。
- [x] 当前例程能否发现目标为 1.0 rad、真实关节因阻挡停在 0.4 rad？
  - 不能。运动循环没有重新读取实际角度或计算跟踪误差，只按照时间继续生成并发送期望角。
- [x] 为什么这个官方例程现在不能直接作为实机抓取控制器？
  - 它缺少有效状态确认、线程同步、完整限位、跟踪误差和异常状态监控、可靠控制周期、目标碰撞检查以及确定的异常退出与控制权释放流程。
